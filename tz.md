# «Рабочий планировщик» — техническое задание

**Версия документа:** 2.0

**Дата:** 19.08.2026

**Статус:** локальный MVP реализован и готовится к финальной приёмке; серверная версия спроектирована, но отложена

**Папка проекта:** `D:\0 кодекс\Planer work`

**Текущий способ публикации:** статический сайт GitHub Pages

**Будущий серверный стек:** Supabase Auth + PostgreSQL + Row Level Security

## 1. Назначение документа

Документ описывает две последовательные фазы одного продукта.

1. **Фаза A — локальный MVP.** Однопользовательский планировщик хранит задачи в `localStorage`, публикуется на GitHub Pages как тестовая статическая версия и после публикации временно замораживается.
2. **Фаза B — серверный сервис.** После отдельного решения о продолжении проект получает общую серверную базу, авторизацию, разделение прав организаций, полноценную мобильную версию и работу из разных браузеров с одними данными.

Фаза B в текущий цикл разработки **не входит**. Её требования зафиксированы заранее, чтобы локальный MVP не развивался в несовместимом направлении.

## 2. Приоритет требований и граница остановки

- До завершения Фазы A исполняемая часть остаётся в `index.html`, `styles.css`, `app.js`.
- До завершения Фазы A сервер, база данных, регистрация и синхронизация не добавляются.
- Следующий практический этап — финальная проверка и публикация текущей версии на GitHub Pages.
- После подтверждённой публикации разработка останавливается.
- Фаза B начинается только по новой прямой команде пользователя.
- При переходе к Фазе B ограничения «три файла», «без сервера» и «только `localStorage`» отменяются.

## 3. Название и язык

- Название продукта: **«Рабочий планировщик»**.
- Интерфейс: русский язык.
- Неделя начинается с понедельника.
- Короткая дата: `ДД.ММ.ГГ`.
- Месяцы и дни недели выводятся по русской локали.

# Часть I. Фаза A — локальный MVP

## 4. Пользователь и назначение Фазы A

В Фазе A работает один локальный владелец. Он видит все сохранённые в текущем браузере организации и задачи и имеет доступ ко всем действиям.

MVP позволяет:

- просматривать месячный календарь;
- создавать задачи одной или нескольким организациям;
- хранить задачи без даты в блокноте;
- выполнять, редактировать, копировать, переносить, сортировать и удалять задачи;
- искать по описанию и фильтровать по организации и состоянию;
- просматривать задачи выбранного дня во всплывающем окне или постоянной левой панели;
- при активном фильтре видеть в левой панели все подходящие задачи за все даты, сгруппированные по месяцам;
- автоматически переносить просроченные невыполненные задачи на текущий день;
- сохранять всё рабочее состояние локально без сети.

## 5. Ограничение локального хранения

Единственный источник данных Фазы A — `localStorage` текущего браузера, профиля и адреса страницы.

Следствия:

- Chrome, Edge, Firefox, Safari и другие браузеры не разделяют один `localStorage`;
- локальный адрес `file://` и адрес GitHub Pages имеют независимые наборы данных;
- публикация кода не переносит текущие задачи на GitHub Pages;
- вход с другого компьютера или телефона не показывает локальные задачи;
- синхронизация вкладок и браузеров отсутствует;
- экспорт и импорт в Фазе A не реализуются;
- пользователю рекомендуется работать с рабочими данными в одном основном профиле до перехода к Фазе B.

Это ожидаемое ограничение Фазы A, а не ошибка чтения.

## 6. Состав проекта Фазы A

Исполняемые файлы:

1. `index.html` — семантическая структура.
2. `styles.css` — визуальное оформление и адаптивные правила.
3. `app.js` — состояние, бизнес-логика, интерфейс и `localStorage`.

Дополнительные документы и исходные материалы:

- `tz.md`;
- `plan.md`;
- `Пример для цветовой гаммы.html`;
- возможная документация публикации.

Требования:

- UTF-8;
- относительные подключения CSS и JavaScript;
- отсутствие фреймворков, сборщиков, серверных компонентов и внешней базы;
- отсутствие абсолютных локальных путей в исполняемом коде;
- прямой запуск двойным щелчком по `index.html`;
- работа после статической публикации на GitHub Pages;
- временные тестовые файлы не входят в коммиты и итоговую поставку.

## 7. Среда и адаптивность Фазы A

Приложение не должно содержать намеренной привязки к бренду браузера и использует стандартные HTML, CSS и JavaScript API.

### 7.1. Контрольные настольные режимы

- `1366×768` при 100%;
- `1366×768` при 125%;
- `1366×768` при 150%;
- `1920×1080` при 100%.

При `1366×768` и 100% календарь помещается в окно без прокрутки документа. Внутренняя прокрутка разрешена в списках задач, блокноте и формах.

### 7.2. Браузеры текущей публикации

Перед публикацией выполняется проверка как минимум в актуальных Chrome, Edge и Firefox. Safari и мобильные браузеры не должны блокироваться намеренно, но полноценная мобильная приёмка относится к Фазе B.

### 7.3. Поведение при уменьшении пространства

- верхняя панель может уплотняться;
- названия организаций в ячейках сокращаются раньше функциональных элементов;
- календарь сохраняет семь колонок;
- текст не перекрывает соседние элементы;
- полное содержание задачи доступно через список дня;
- необходимые списки получают внутреннюю прокрутку.

## 8. Основной экран

### 8.1. Шапка

Содержит:

- название **«Рабочий планировщик»**;
- кнопку **«Отобразить задачи» / «Скрыть задачи»** слева;
- кнопки предыдущего и следующего месяца;
- название месяца и года;
- кнопку **«Сегодня»**;
- кнопку **«Блокнот»**;
- кнопку **«Создать новую задачу»**.

Постоянная надпись **«Локальные данные готовы»** и цветная точка не показываются. Ошибки хранения выводятся только при фактической ошибке.

### 8.2. Поиск и фильтры

Панель содержит:

- поиск по описанию;
- фильтр одной организации;
- фильтр состояния: все, невыполненные, выполненные;
- кнопку **«Сбросить»**.

### 8.3. Календарь

- Сетка: семь колонок и шесть строк.
- Дни недели: Пн–Вс.
- Ячейки соседних месяцев пустые и неактивные.
- Текущий день выделен зелёной рамкой.
- Выбранный день имеет отдельный мягкий зелёный фон.
- Навигация выполняется кнопками и вертикальным колесом мыши над календарём.
- Один жест колеса переключает один месяц; `Ctrl/Command + колесо` не перехватывается.
- Кнопка **«Сегодня»** возвращает текущую дату.

### 8.4. Содержимое дня

В ячейке показываются:

1. число;
2. общий счётчик всех подходящих задач;
3. до четырёх строк задач при достаточном месте.

Подпись задачи:

- одна организация — название организации;
- несколько организаций — **«Общая задача»**;
- одинаковые общие задачи показываются отдельными строками, не объединяются;
- выполненная задача остаётся в ячейке, отображается бледно и зачёркнуто;
- пятая и последующие задачи учитываются счётчиком и доступны в полном списке.

## 9. Просмотр задач дня

Предусмотрены два режима.

### 9.1. Всплывающее окно

- Открывается нажатием на день, если постоянная панель скрыта.
- Календарь остаётся видимым под затемнением.
- Закрывается крестиком; стандартный `Esc` допускается.
- Клик по затемнённому фону не закрывает окно.
- После закрытия фокус возвращается в исходный день.
- При смене месяца окно закрывается.

### 9.2. Постоянная левая панель

- Включается верхней кнопкой.
- Без активных фильтров показывает задачи выбранного дня.
- Нажатие на другой день обновляет панель без всплывающего окна.
- При активном поиске или фильтре показывает все подходящие календарные задачи со всеми датами.
- Результаты сортируются хронологически.
- Каждый месяц образует отдельный визуальный блок: заголовок месяца и только его карточки внутри блока.
- Месяц, открытый в календаре, выделяется зелёной рамкой, мягким фоном и боковым акцентом.
- У каждой найденной задачи показывается короткая дата.
- Выбор дня не сужает отфильтрованный список.
- Создание задачи из панели результатов отключено, поскольку единая дата не выбрана.
- После сброса панель возвращается к режиму выбранного дня.

## 10. Организации Фазы A

### 10.1. Поля

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | UUID-строка | уникально и неизменно |
| `name` | строка | отображаемое название |
| `normalizedName` | строка | сравнение без регистра и лишних пробелов |
| `archived` | boolean | совместимость с внутренней моделью; активный интерфейс архивирования отсутствует |
| `createdAt` | ISO-дата-время | техническое поле |
| `updatedAt` | ISO-дата-время | техническое поле |

### 10.2. Ввод

- Свободный ввод и `Enter`.
- Название: 1–100 символов.
- Внутренние повторные пробелы сокращаются.
- Дубли без учёта регистра запрещены.
- В одной задаче не более пяти организаций.
- Существующие организации предлагаются в подсказках.

### 10.3. Переименование

- Двойной щелчок по метке организации открывает отдельное окно **«Изменить организацию»**.
- `Enter` на сфокусированной метке выполняет то же действие.
- Окно явно сообщает, что меняется организация глобально, а не состав одной задачи.
- Меняется только название и время обновления; `id` и связи задач сохраняются.
- Пустое и дублирующее название блокируются.
- Состав организаций конкретной задачи изменяется только через редактирование задачи.
- Неиспользуемые организациями записи удаляются из локального справочника после изменения или удаления связанных задач.

## 11. Модель задачи Фазы A

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | UUID-строка | уникально |
| `organizationIds` | массив UUID | 1–5 для календаря; 0–5 для блокнота |
| `date` | `YYYY-MM-DD` или `null` | `null` означает блокнот |
| `description` | строка | 1–3000 символов |
| `completed` | boolean | при создании `false`; в блокноте `false` |
| `order` | число или `null` | порядок внутри группы дня; в блокноте `null` |
| `edited` | boolean | признак сохранённой корректировки |
| `autoCarried` | boolean | текущая отметка автопереноса, не история |
| `createdAt` | ISO-дата-время | техническое поле |
| `updatedAt` | ISO-дата-время | техническое поле |

Описание является обычным многострочным текстом. HTML и JavaScript не исполняются, ссылки автоматически не активируются, переносы строк сохраняются.

В Фазе A общая задача остаётся одной записью с общей датой, описанием, порядком и галочкой для всех организаций.

## 12. Диапазон дат

- Просматривать календарь можно без ограничения по прошлым и будущим месяцам.
- Создавать, назначать и вручную переносить задачу можно от сегодняшнего дня до той же календарной даты следующего года включительно.
- Для 29 февраля последняя дата невисокосного следующего года — 28 февраля.
- Прошедшие даты доступны для просмотра, но не для создания новой задачи.
- Все бизнес-даты сравниваются как локальные календарные даты без UTC-сдвига.

## 13. Создание и блокнот

### 13.1. Создание из дня

- Форма получает выбранную дату.
- Для календарной задачи обязательны 1–5 организаций и описание.
- Дату можно очистить; тогда задача сохраняется в блокнот.
- Новая календарная задача становится первой среди невыполненных.

### 13.2. Общая кнопка

- Открывает пустую форму без даты и организаций.
- Без даты создаётся задача блокнота.
- При выборе даты начинают действовать правила календарной задачи.

### 13.3. Блокнот

- Содержит задачи с `date = null`.
- Организации необязательны, описание обязательно.
- Галочка и стрелки порядка не показываются.
- Доступны редактирование, копирование, удаление и назначение даты.
- Дату можно назначить из списка либо из открытой карточки редактирования.
- При назначении даты та же запись с тем же `id` исчезает из блокнота и становится календарной.
- Если нужна повторяемая заготовка, сначала создаётся копия, затем дата назначается копии.
- Копию блокнота можно оставить без даты или сразу создать календарной; оригинал не изменяется.

## 14. Карточка и действия

- Сначала карточка компактная.
- Одновременно раскрыта одна карточка.
- Раскрытая карточка выделяется светло-зелёным фоном, зелёной рамкой и мягкой тенью.
- Действия отображаются компактными иконками с русскими доступными именами и одной визуальной подсказкой.
- Доступны: редактирование, копирование, удаление, перенос, перенос в блокнот, `↑`, `↓` с учётом состояния.
- Опасное удаление получает красный акцент только при взаимодействии.

## 15. Выполнение и порядок

### 15.1. Галочка

- Галочка доступна в компактном списке и меняет статус без раскрытия второй карточки.
- Выполненная задача приглушается, зачёркивается и перемещается после невыполненных.
- Выполненная задача остаётся в ячейке календаря бледной и зачёркнутой.
- Снятие галочки у сегодняшней или будущей задачи возвращает её в начало невыполненных.
- Снятие галочки у прошедшей задачи переносит её на сегодня и ставит `autoCarried = true`.
- Выполненную задачу нельзя перенести или отправить в блокнот напрямую; её можно копировать.

### 15.2. Порядок

- Невыполненные всегда выше выполненных.
- Новая, назначенная или вручную перенесённая задача становится первой среди невыполненных.
- Копия невыполненной задачи в том же дне располагается сразу после оригинала.
- Выполненная задача уходит в конец выполненной группы.
- Стрелки перемещают только внутри текущей группы.
- При активном поиске или фильтре стрелки отключены с подсказкой о сбросе.

## 16. Редактирование, копирование, перенос и удаление

### 16.1. Редактирование

- Разрешены организации, описание и дата невыполненной задачи.
- Очистка даты отправляет задачу в блокнот.
- Дата выполненной задачи не меняется через редактирование.
- После сохранения `edited = true`, показывается `★ изменено`.
- Автопереносная отметка очищается.
- При закрытии изменённой формы предлагаются **«Сохранить»**, **«Не сохранять»**, **«Отмена»**.

### 16.2. Ручной перенос

- Доступен только невыполненной календарной задаче.
- Новая дата входит в годовой диапазон и отличается от текущей даты задачи.
- Старое место и история переноса не сохраняются.
- Задача становится первой среди невыполненных нового дня.

### 16.3. Автоперенос

Проверяется при загрузке, возвращении вкладки и фокусе окна после смены даты.

- Все просроченные невыполненные календарные задачи переносятся прямо на сегодня.
- Промежуточные даты и старое место не сохраняются.
- Старейшие задачи располагаются выше более новых внутри переносимого блока.
- Ставится `autoCarried = true` и метка `↷ перенесено`.
- Метка очищается после редактирования, выполнения или ручного переноса.
- Выполненные задачи и блокнот не переносятся.

### 16.4. Копирование

- Копия получает новый `id`, пустую галочку, `edited = false`, `autoCarried = false`.
- Оригинал не изменяется.
- Копию календарной задачи можно сохранить на дату или в блокнот.
- Копию блокнота можно оставить без даты либо сделать календарной.

### 16.5. Удаление

- Каждое удаление требует подтверждения.
- Для общей задачи указывается количество организаций.
- Корзины и восстановления нет.
- Успех показывается только после успешной записи `localStorage`.

## 17. Поиск и фильтры

- Поиск работает только по описанию.
- Обновление происходит после каждого символа.
- Регистр не учитывается; пробелы по краям запроса игнорируются.
- Фильтр организации допускает одну организацию.
- Фильтр состояния: все, невыполненные, выполненные.
- Условия объединяются логическим **И**.
- В блокноте применяются поиск и организация, но не статус.
- Кнопка **«Сбросить»** очищает все условия одним действием.
- При отсутствии результата показываются **«Задачи не найдены»** и кнопка сброса.
- Поиск и фильтры не сохраняются после перезагрузки.

## 26. Основные сценарии Фазы A

### A-01. Создание из дня

Выбрать допустимый день, добавить организацию и описание, сохранить. Задача появляется первой среди невыполненных.

### A-02. Создание в блокноте

Нажать общую кнопку, оставить дату пустой, сохранить описание. Задача появляется в блокноте.

### A-03. Назначение даты

Назначить дату задаче блокнота. Та же запись с тем же `id` исчезает из блокнота и появляется в календаре.

### A-04. Общая задача

Добавить 2–5 организаций. Создаётся одна карточка с единым состоянием и фильтруется каждой организацией.

### A-05. Выполнение

Поставить галочку. Задача приглушается, зачёркивается и уходит вниз. Снять галочку — вернуть в работу по правилам даты.

### A-06. Перенос

Перенести невыполненную задачу на другую допустимую дату. Старое место не сохраняется.

### A-07. Автоперенос

Открыть приложение после пропущенных дней. Просроченные невыполненные задачи находятся сегодня и отмечены переносом.

### A-08. Фильтр и постоянная панель

Открыть левую панель, включить поиск или фильтр. Панель показывает все подходящие даты, разделённые на месячные блоки.

### A-09. Глобальное переименование организации

Дважды щёлкнуть метку, изменить название. Новый текст появляется во всех связанных задачах, `id` не меняется.

### A-10. Ошибка хранения

Имитировать повреждённый JSON или отказ записи. Приложение не показывает ложный успех и не удаляет данные без подтверждения.

### A-11. Локальный и опубликованный адрес

Открыть локальную и GitHub Pages версии. Интерфейс одинаков, но данные независимы.

# Часть II. Фаза B — серверный многопользовательский сервис

## 27. Статус Фазы B

Все требования этой части имеют статус **«спроектировано, разработку не начинать»**.

Старт возможен только после:

- завершения и фиксации Фазы A;
- отдельного решения пользователя;
- повторного согласования стоимости, провайдера и порядка миграции данных.

## 28. Цель Фазы B

Создать единый интернет-сервис, в котором:

- владелец видит все организации, пользователей и задачи;
- пользователи входят со своих устройств и браузеров;
- область доступа определяется организацией;
- организация видит и изменяет только свои записи;
- организация создаёт задачи только для себя;
- данные хранятся на сервере и одинаковы после входа в любом поддерживаемом браузере;
- интерфейс полноценно работает на компьютере, планшете и телефоне.

## 29. Целевая архитектура Фазы B

Рекомендуемая первая серверная реализация:

- статический или собранный веб-интерфейс;
- Supabase Auth для пользователей и сессий;
- PostgreSQL как единственный источник рабочих данных;
- Supabase Data API;
- Row Level Security для ограничения каждой операции;
- SQL-миграции схемы в Git;
- серверное расписание для автопереноса;
- GitHub Pages либо другой HTTPS-хостинг фронтенда.

Интерфейс не обращается к `localStorage` как к источнику задач. `localStorage` допускается только для несекретных настроек интерфейса и управляемой библиотекой сессии.

Закрытый ключ `service_role` никогда не попадает во фронтенд или публичный Git. Клиент использует только публичный ключ, безопасность обеспечивается RLS.

## 30. Модульная структура Фазы B

Ограничение трёх файлов снимается. Код разделяется минимум на:

- `ui` — отображение и взаимодействие;
- `domain` — правила задач, дат и состояний;
- `auth` — сессия и текущий пользователь;
- `data` — интерфейс репозитория и серверная реализация;
- `migrations` — схема, ограничения и RLS;
- `tests` — модульные, интеграционные и доступные браузерные проверки.

UI не содержит прямых SQL-правил и не решает, имеет ли пользователь право на чужую строку. Окончательное решение принимает база/API.

## 31. Пользователи и роли Фазы B

Аутентификация выполняется для отдельного человека, а область доступа — на уровне организации. Общий пароль, записанный в сущности организации, не используется.

Первоначально у организации может быть одна учётная запись. Схема должна позволять позже добавить несколько пользователей без миграции задач.

Роли:

| Роль | Права |
| --- | --- |
| `owner` | полный доступ ко всем организациям, пользователям, задачам и назначениям |
| `organization_user` | чтение и изменение только записей своей организации; создание только для своей организации |

Регистрация публичным пользователем по умолчанию закрыта. Владелец приглашает пользователя и связывает его с организацией.

## 32. Матрица доступа Фазы B

| Операция | `owner` | `organization_user` |
| --- | --- | --- |
| видеть организации | все | только свою |
| переименовать организацию | да | нет |
| видеть пользователей | все | только себя; список коллег — отдельное будущее решение |
| видеть задачи | все | только задачи своей организации |
| создать одиночную задачу | для любой организации | только для своей |
| создать общую задачу | да | нет |
| изменить описание/дату одиночной задачи | да | да, только своей |
| изменить своё выполнение и порядок | да | да |
| изменить назначение другой организации | да | нет |
| удалить общую группу | да | нет |
| удалить свою одиночную задачу | да | допускается; окончательно подтвердить перед разработкой |
| управлять пользователями | да | нет |

Кнопки интерфейса отражают права, но защита обязательно дублируется RLS. Подмена запроса в браузере не должна давать доступ к чужим данным.

## 33. Серверная модель данных

### 33.1. Основные таблицы

| Таблица | Назначение |
| --- | --- |
| `auth.users` | учётные записи провайдера Auth |
| `profiles` | профиль и глобальная роль пользователя |
| `organizations` | организации со стабильными UUID |
| `organization_members` | связь пользователя с организацией и ролью |
| `task_groups` | логическая одиночная или общая задача |
| `organization_tasks` | отдельная рабочая запись конкретной организации |
| `migration_batches` | контроль однократного импорта локальных данных |

### 33.2. Почему задача разделяется на группу и записи организаций

Фаза A хранит общую задачу одной записью с одной галочкой. В многопользовательском сервисе это небезопасно: изменение одной организацией затронуло бы остальные.

В Фазе B:

- `task_groups` связывает записи одной общей операции;
- `organization_tasks` содержит `organization_id`, описание, дату, выполнение, порядок и признаки конкретной организации;
- владелец может видеть связанные записи как одну общую группу;
- каждая организация изменяет только свою строку;
- выполнение или перенос одной организации не меняет остальные.

### 33.3. Минимальные поля `organization_tasks`

- `id` UUID;
- `task_group_id` UUID;
- `organization_id` UUID;
- `description` text;
- `scheduled_date` date или `null`;
- `completed` boolean;
- `sort_order` integer или `null`;
- `edited` boolean;
- `auto_carried` boolean;
- `created_by` UUID;
- `updated_by` UUID;
- `created_at` timestamptz;
- `updated_at` timestamptz;
- `version` integer для контроля конкурентных изменений.

Уникальность пары `task_group_id + organization_id` предотвращает двойное назначение одной общей задачи организации.

## 34. RLS и серверная безопасность

Для каждой пользовательской таблицы включается RLS с политикой запрета по умолчанию.

Обязательные негативные проверки:

- неавторизованный запрос не читает задачи;
- пользователь организации A не читает организацию B;
- пользователь A не создаёт запись с `organization_id` B;
- пользователь A не изменяет и не удаляет запись B;
- пользователь организации не повышает себе роль;
- клиентский запрос не обходит ограничения изменением JSON;
- владелец выполняет разрешённые глобальные операции.

Пароли хранит Auth-провайдер в хешированном виде. Пароли, refresh-токены и закрытые ключи не записываются в таблицы приложения, логи или Git.

## 35. Серверные бизнес-процессы

- Автоперенос выполняется серверным расписанием в часовом поясе `Europe/Moscow`, а не зависит от открытия браузера.
- Множественные запуски одной операции должны быть идемпотентными.
- Изменения записывают `updated_by`, `updated_at` и `version`.
- При конфликте версий интерфейс не затирает чужое изменение молча, а предлагает обновить данные.
- После успешной серверной записи все представления обновляются из ответа сервера.
- Realtime-синхронизация открытых экранов необязательна для первой серверной версии; после повторного входа или обновления данные обязаны совпадать.

## 37. Миграция из Фазы A

До миграции создаётся локальный резервный JSON текущего `workPlanner.state.v1`. Импорт выполняется владельцем однократно.

Требования:

1. Проверить версию и структуру JSON.
2. Сохранить UUID организаций.
3. Одиночную задачу преобразовать в одну `task_group` и одну `organization_task`.
4. Общую задачу преобразовать в одну `task_group` и отдельную `organization_task` для каждой организации.
5. Задачу блокнота без организации назначить владельцу как личную либо потребовать решение перед импортом.
6. Сохранить даты, описания и технические отметки, насколько они совместимы.
7. Сделать импорт идемпотентным по `migration_batch` и исходным UUID.
8. Сравнить количество организаций, логических задач и назначений до и после.
9. Не удалять локальный источник до письменного подтверждения приёмки.

## 38. Критерии приёмки Фазы B

1. Владелец входит и видит все данные.
2. Пользователь организации входит из любого поддерживаемого браузера и видит только свою организацию.
3. Организация A не получает данные B ни через интерфейс, ни прямым API-запросом.
4. Организация создаёт задачу только для себя.
5. Общая задача владельца создаёт отдельные связанные записи организаций.
6. Изменение одной организации не меняет запись другой.
7. После входа в Chrome, Firefox, Safari или мобильном браузере отображаются одни серверные данные.
8. Пароли и закрытые ключи отсутствуют в клиентском коде и Git.
9. Автоперенос выполняется без открытой страницы.
10. Конфликт одновременного редактирования не приводит к молчаливой потере данных.
11. Миграция локального набора проходит повторяемо и подтверждается контрольными количествами.
12. Мобильный интерфейс проходит контрольные размеры и сенсорные сценарии.

## 39. Основные сценарии Фазы B

### B-01. Вход владельца

Владелец авторизуется и получает все организации и задачи.

### B-02. Вход организации

Пользователь организации авторизуется и получает только её записи.

### B-03. Запрет чужой организации

Пользователь подменяет запрос на чужой `organization_id`; сервер возвращает отказ без данных.

### B-04. Создание организацией

Организация создаёт задачу; сервер принудительно связывает её только с доступной организацией.

### B-05. Общая задача владельца

Владелец выбирает несколько организаций; создаётся одна группа и отдельное назначение каждой организации.

### B-06. Независимое выполнение

Организация A выполняет свою запись. Состояние B не меняется.

### B-07. Разные браузеры

Один пользователь входит в двух браузерах. После обновления оба показывают одно серверное состояние.

### B-08. Мобильная работа

Пользователь входит с телефона, открывает день, создаёт и выполняет задачу без горизонтальной прокрутки и hover-действий.

### B-09. Конфликт

Два пользователя изменяют одну разрешённую запись. Второе устаревшее сохранение получает конфликт и не затирает первое молча.

### B-10. Миграция

Владелец импортирует проверенный локальный JSON, сверяет контрольные количества и подтверждает переход.

## 40. Не входит в текущий цикл

До отдельного старта Фазы B не выполняются:

- Supabase-проект и таблицы;
- регистрация и вход;
- серверные пользователи организаций;
- RLS;
- серверный автоперенос;
- общие данные между браузерами;
- импорт локальных задач на сервер;
- полноценная мобильная переработка;
- совместное редактирование и Realtime;
- серверное резервное копирование;
- публикация секретов или создание платной инфраструктуры.

## 41. Решения, требующие подтверждения перед Фазой B

Перед серверной разработкой пользователь отдельно подтверждает:

1. Supabase как провайдера либо собственный backend.
2. Разрешено ли организации удалять свои одиночные задачи.
3. Нужны ли нескольким людям отдельные аккаунты внутри одной организации уже в первой серверной версии.
4. Как обрабатывать блокнотные задачи без организации при миграции.
5. Нужна ли организациям собственная заметка к общей задаче.
6. Требуется ли Realtime или достаточно обновления после сохранения/перезагрузки.
7. Домен и место размещения фронтенда после тестовой GitHub Pages версии.

До ответов используются рекомендации этого документа, но серверный код не создаётся.
